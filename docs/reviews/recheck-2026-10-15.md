# Issue recheck and working evidence — 15 October 2026

Rechecked the previously reported issues against the current implementation, reran the complete automated suites and exercised the real Electron application with disposable SQLite data. This run found and fixed two additional cache-coherency gaps. The workshop database was not opened or changed by these checks.

## New fixes from this recheck

1. **Stock changes left other screens stale.** Receipt posting only refreshed the inventory register; cached item/batch selectors could retain old quantities for two minutes. A shared stock invalidation function now covers receipts, job-part consumption, return approvals, inventory operations, count decisions, item edits, starter catalogue loading and sales reservations. It refreshes inventory dashboard data as well. Active queries reload immediately; inactive queries reload when reopened.
2. **Reference edits left selectors stale.** Saving/deleting a reference master refreshed its register but missed both URL-keyed and named selectors used elsewhere. Master changes now invalidate both selector families, including selected-record lookups. Vehicle master edits also refresh service-history selectors.

Four new regression tests cover purchase-triggered invalidation across six cache families, active batch refetch from quantity 1 to 5, unrelated-cache preservation, warehouse selector refresh and clearing a selector without retaining the old record. Clearing already worked correctly; that check required no product change.

The warehouse regression failed before its fix and passed afterward: [before](evidence/recheck-cache-before-2026-10-15.txt), [after](evidence/recheck-cache-after-2026-10-15.txt). The before log was captured after the stock fix and therefore demonstrates the reference-master gap specifically. Tests: [recheck regressions](../../tests/renderer/recheck-regressions.test.jsx).

## What cannot be established in this workspace

- Clean Windows installation, UAC, uninstall and upgrade from a known old release require a separate clean machine or VM.
- A trusted installer signature requires the owner's signing certificate or signing-service credentials.
- Tally compatibility requires importing the exported XML into an actual disposable TallyPrime company and reviewing it with its operator/accountant.
- Workshop acceptance requires staff testing, real printing and accountant reconciliation of opening/historical balances.
- Missing or ambiguous historical purchase/return identity requires source documents and human reconciliation. The application must not guess and adjust the wrong party's accounts.

No remote CI execution, clean-machine installation, real Tally import or exhaustive manual acceptance is claimed by these local checks.
